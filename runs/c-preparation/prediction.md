# 任务 C 测前预测

记录日期：2026-11-25；在 C1、C2 开始之前写入。C3 的实测用量和配额另在 C1 完成后、C3 开始前记录。

沿用 B0 的容量线 C=80 请求/秒，固定 3 个实例，负载 2C=160 请求/秒。实例绑定 CPU 1，配额 25%，默认预热 60 秒、模拟拉镜像 20 秒；loadgen、lbd、scaler 和监控绑定 CPU 0。

## C1：停止与卡住

默认健康检查每 1 秒一次、超时 500 ms、连续失败 3 次。若只靠健康检查，进程退出的连接拒绝会立即返回，预计 2～3 秒判 down；按 160/3≈53.3 请求/秒分流，约 107～160 个请求失败。但 scaler 每秒 reconcile 一次，能读到 systemd 的 failed/inactive，预计实际先在 0～1 秒内 removed，约 0～53 个请求失败。补建预计再需约 20+60+2～5=82～85 秒。

暂停一台 20 秒时，systemd 仍报告进程 active，scaler 无法靠进程状态发现；检查超时需要额外 0.5 秒，预计注入后 2.5～3.5 秒 down，约 133～187 个请求被分给卡住的实例并最终失败。恢复后连续两次成功，预计注入后约 21～22 秒 up。客户端与代理超时都是 2 秒；逐秒数据按计划发送时刻归桶，不能把错误桶当成响应实际返回时刻。

## C2：全体暂停 2 秒

宽松参数通常来不及累计三次连续失败，预计不判 down；暂停边界附近可能有少量 2 秒超时，恢复后积压请求还会抬高延迟。灵敏参数每 500 ms 检查、超时 200 ms、fall=1，预计 0.2～0.7 秒内判 down，全部摘除后直接返回 503；恢复仍需 rise=2，预计注入后约 2.5～3 秒恢复。预计灵敏组错误更多，体现短暂抖动下快速检出与误判之间的取舍。
